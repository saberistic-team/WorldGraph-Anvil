# Productive commerce schema and data dictionary

This document describes the Milestone 09 productive-commerce storage model introduced by `0010_production_business_market_tax.sql`, its private projection-repair extension in `0011_commerce_projection_repair.sql`, and the frozen authority/reconciliation/outbox-retry boundary in `0012_commerce_reconciliation_integrity.sql`. It complements `economy.md`: the Milestone 08 financial journal and asset-title tables remain the only authority for currency balances, supply, and ownership, while the tables below add resources, inventory, businesses, production, employment, market trades, taxes, an independently reconciled commerce projection, and narrowly reviewed repair evidence.

All rows are world-scoped. Composite foreign keys prevent cross-world references. UUIDs are storage identities; stable keys are deterministic design identities where present. Commands, events, ledger entries, outbox references, and the world runtime revision remain shared with the existing authoritative command boundary.

## Numeric and lifecycle conventions

- Resource quantities are exact canonical decimals at JSON boundaries, scaled bigint atoms in the pure domain, and `numeric(30,12)` in PostgreSQL. Each `resource_types.quantity_scale` is 0 through 12 and rejects excess precision.
- Currency remains signed 64-bit minor units under the Milestone 08 accounting model. A resource unit price is a positive integer number of currency minor units.
- `row_version` is optimistic aggregate concurrency. `created_state_revision`, `updated_state_revision`, `terminal_state_revision`, and plain `state_revision` bind rows to the shared world ledger revision.
- Lifecycle rows retain their creating and terminal command/event identities. Terminal transitions are one-way and database guarded.
- Hashes and checksums are 32-byte SHA-256 values over canonical, domain-separated documents. Timestamps are operational evidence; simulation ticks determine economic time.
- `PerformJobV1`, `StartProductionRunV1`, `CreateMarketListingV1`, and `PurchaseMarketListingV1` command records carry a mandatory immutable `rate_limit_scope_hash`. The scope is derived from the command type and its contract, facility, seller-inventory, or listing target respectively. Durable per-world/actor/type/target command history, rather than process memory, is the velocity authority.

## Inventory and reservations

| Table                    | Role                                                                                                                                                      | Mutability and important invariants                                                                                                                                                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inventories`            | Current quantity and reserved quantity for one owner, resource, and optional container asset.                                                             | Guarded projection. Unique owner/container/resource tuple. `0 <= reserved_quantity <= quantity`; available is derived, never separately stored.                                                                                                 |
| `inventory_movements`    | Immutable journal of mint/consume/transfer-style resource movement, with from/to inventories, source type/ID/ordinal, command, event, tick, and revision. | Append-only fact. At least one endpoint; endpoints differ; quantity positive; source and command ordinals prevent duplicate effects.                                                                                                            |
| `inventory_reservations` | Exact quantity held for a production input or market listing.                                                                                             | Guarded lifecycle aggregate. One reservation per purpose/inventory. `active` transitions once to `consumed`, `released`, or `expired`; listing reservations require an expiry tick. Every terminal row carries command/event/revision evidence. |

The sum of active reservations for an inventory equals its `reserved_quantity`. Production consumes reservations only at completion. Listing purchase consumes only the bought fraction; cancellation or expiry releases the remainder.

## Business and production

| Table                        | Role                                                                                                                                                  | Mutability and important invariants                                                                                                                                                                                                                                  |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `businesses`                 | Runtime business backed by one organization entity and one organization wallet/currency.                                                              | Guarded aggregate. One business per backing organization and one business per wallet. Status is `active`, `suspended`, or terminal `closed`; metadata is bounded inert JSON.                                                                                         |
| `business_facilities`        | A business-operated facility bound to a world asset and inventory container, with capacity/configuration.                                             | Guarded aggregate. Same-world business/asset links; status `active`, `disabled`, or `retired`; row version controls reconfiguration.                                                                                                                                 |
| `production_runs`            | One execution of an exact recipe version at one facility, with input/output snapshots, start/due/completion ticks, schedule ID, and failure evidence. | Guarded lifecycle aggregate. `scheduled` transitions through `reserving` and `ready` to `completed`, or terminates as `failed`/`cancelled`; one durable schedule and one terminal command/event. Output destination remains the configured facility asset container. |
| `production_run_transitions` | Immutable ordered transition history for a run.                                                                                                       | Append-only fact with unique ordinal and command/event identity.                                                                                                                                                                                                     |

Starting production validates the facility recipe allowlist, snapshots exact quantities, reserves all inputs atomically, and creates a durable scheduled action. Completion either consumes every reservation and journals every output or records failure without a partial resource effect.

## Employment and payroll

| Table                  | Role                                                                                                                                                        | Mutability and important invariants                                                                                                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `employment_offers`    | Immutable business-authored role, wage rule, cadence, capacity, cooldown, effective ticks, and currency terms.                                              | Append-only offer definition with bounded `open`, `closed`, or `retired` status semantics defined by code-owned commands.                                              |
| `employment_contracts` | Worker-to-business agreement created from an exact offer, including status, capacity slot, wage terms, cooldown state, row version, and lifecycle evidence. | Guarded lifecycle aggregate. `offered -> active -> ended` or cancellation; active capacity and duplicate-worker rules are constrained transactionally.                 |
| `work_records`         | Immutable evidence that a worker performed an authorized job at a tick, including contract/business/facility/recipe context and output basis.               | Append-only fact. | `payroll_records`      | Deferred wage obligation, tax-policy snapshot, gross/tax/net amounts, schedule identity, and settlement/failure transaction evidence.                       | Guarded lifecycle aggregate. `pending` transitions once to `paid` or `failed`; paid rows reference one balanced financial transaction, and failed rows reference none. |

Tax is selected and snapshotted at the work tick. Later policy changes cannot alter a pending payroll record. Worker, business manager, and privileged operator views are authorized before pagination.

## Market, tax, and treasury

| Table             | Role                                                                                                                                                                                                                   | Mutability and important invariants                                                                                                                                                                                   |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `market_listings` | Fixed-price sale of one resource from one seller inventory to one seller wallet, with offered/remaining/reserved quantity and expiry schedule.                                                                         | Guarded lifecycle aggregate. `open` transitions once to `filled`, `cancelled`, or `expired`; an open listing reserves exactly its remainder. Unit price positive. Purchase requires current tick `< expires_at_tick`. |
| `market_trades`   | Immutable buyer/seller, inventory transfer, quantity, unit price, gross, tax, fee, net, transaction, tick, and idempotency evidence.                                                                                   | Append-only fact. Buyer and seller differ; `buyer_total = seller_net + tax + fee`; one command/event/financial transaction per trade.                                                                                 |
| `tax_policies`    | Immutable compiler-authored transaction, sales, payroll, periodic-flat, or marketplace-fee policy, with effective ticks, collection mode, rate/amount, applicability, primitive provenance, source plan, and checksum. | Append-only policy fact. Percentage rates are bounded basis points; periodic policies name an exact payer entity/wallet and interval; active half-open effective windows cannot overlap within one semantic scope.    |
| `tax_assessments` | Immutable application of one policy to one market trade, payroll, or periodic charge, including payer, treasury, basis, amount, settlement transaction, tick, command, and event.                                      | Append-only fact. Unique per policy/source/payer and transaction/policy/payer; payer and treasury wallets differ.                                                                                                     |

One tax-policy scope is world, currency, tax type, and normalized applicability. Non-periodic applicability is `{}`. Periodic applicability retains payer entity and payer wallet but excludes `intervalTicks`, because cadence is a policy term rather than a distinct taxable scope. Effective intervals are `[effective_from_tick,effective_until_tick)`, with a null upper bound treated as infinity; adjacent intervals are valid. Pure seed-plan/compiler validation rejects overlap before persistence, while migration `0012` validates retained rows and adds a `btree_gist` exclusion constraint for concurrent PostgreSQL enforcement.

Treasury money is not stored in these tables. A compiled treasury binding selects an ordinary M08 treasury wallet, and every receipt is an ordinary balanced posting in `financial_transactions`/`wallet_postings`. `TreasuryRevenueRecordedV1` provides domain/history evidence but does not create a second balance.

## Reconciliation and write gates

| Table                                    | Role                                                                                                                                                                                                                                                                                                                       | Visibility and mutability                                                                                      |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `economy_expansion_reconciliation_runs`  | Source revision/sequence, live and rebuilt checksums for inventory, reservations, trades, payroll, tax, aggregate projection, counts, status, command, and event. Current head is reconciliation schema 3 (`2` retained).                                                                                                  | Immutable bounded evidence. Member-facing status exposes safe summaries; detailed evidence is operator scoped. |
| `economy_expansion_reconciliation_items` | Ordered mismatch details for inventory quantity/reservation, reservation lifecycle, recipe version, tax policy, governance tax-policy lineage, business, facility, production, employment contract, listing/trade, payroll, tax assessment, or projection checkpoint, with hashed key and canonical expected/actual value. | Immutable sensitive evidence. Not an ordinary member API.                                                      |
| `commerce_projection_repair_plans`       | Private 15-minute dry-run seal binding world/core/expansion heads, latest mismatch reconciliation, exact reason, reserved effect identities, and canonical plan hash.                                                                                                                                                      | Immutable owner/operator evidence. No application-role or public API access.                                   |
| `commerce_projection_repair_plan_items`  | UUID-sorted, ordinal-contiguous affected inventories with exact row version, live/rebuilt quantity and reservation values, mismatch kinds, and reserved repair-fact ID.                                                                                                                                                    | Immutable private plan detail; every item must represent a real journal-derived delta.                         |
| `commerce_projection_repair_approvals`   | One exact plan/hash approval from an active platform administrator distinct from the preparer.                                                                                                                                                                                                                             | Append-only private approval and idempotency evidence.                                                         |
| `commerce_projection_repair_facts`       | One immutable before/after projection correction fact per approved plan item, linked to the repair command and event.                                                                                                                                                                                                      | Append-only repair authority; it does not replace or mutate an inventory movement or reservation fact.         |
| `commerce_projection_repair_executions`  | Idempotent execution receipt binding plan, approver/executor, command, repair event/ledger entry, repair facts, post-repair matched reconciliation, heads, and checksum.                                                                                                                                                   | Append-only private execution evidence; exact replay returns the original effect.                              |

Reconciliation derives a new document from immutable facts and compares it with live projections. It never edits a projection. Schema-2 reconciliation binds exact recipe-version and tax-policy provenance as well as complete production authority: the frozen initial transition, input/output snapshots and checksum; terminal transition; reservation terminal evidence; exact production movement envelopes; and the terminal production events. A completed run requires `ResourcesConsumedV1` at aggregate version 2/event ordinal 0 and `ResourcesProducedV1` at aggregate version 3/event ordinal 1. A failed run requires `ProductionFailedV1` at aggregate version 2/event ordinal 0 and no resource movement. Thus aggregate versions 2 and 3 are production event evidence within reconciliation schema 2, not new reconciliation schema versions. Schema 3, published by migration `0013`, retains that comparison surface and adds `governance_tax_policy_lineage` so governed tax authority can be reconciled without inventing commerce rows.

The private `RepairEconomicProjectionV1` workflow is a narrow recovery exception: preparation changes no world projection, requires the latest mismatch reconciliation at unchanged core/expansion/runtime/ledger heads, and seals only inventory quantity/reservation rows whose rebuilt journal values differ. A distinct active platform administrator approves the exact hash; that same administrator executes through an owner-authorized session before the 15-minute expiry. Execution appends one repair fact per item, updates only those guarded inventory projection fields, appends the private repair command/event plus approval override and repair-anchor ledger evidence, and creates an exact post-repair matched reconciliation/current checkpoint in one transaction. It never updates/deletes movements, reservations, production facts, work/payroll facts, trades, tax assessments, commands, events, or ledger entries. It is absent from the public registry and all HTTP routes.

## Dead-outbox retry evidence

| Table                  | Role                                                                                                                                                                                                                 | Visibility and important invariants                                                                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `outbox_retry_intents` | Append-only operator intent binding a retry UUID, world/message, active platform administrator, security audit row, bounded reason, prior attempt count, one-transaction gate hash, and canonical requeue timestamp. | Private operator evidence. The application role has no table privileges; update/delete is rejected; message/world and audit/world/actor identities are foreign-keyed. |

`worldgraph_retry_dead_outbox_message` is an owner-only `SECURITY DEFINER` function with `PUBLIC` and application-role execution revoked. It requires an unlocked `dead` message, an active platform administrator, a 20–1000-code-point reason, the exact `RETRY DEAD OUTBOX MESSAGE` confirmation, and a caller-supplied retry UUID. Under the world advisory lock it appends the audit/intent, opens a transaction-local secret gate, and moves the original message from `dead` to `pending`. It preserves message ID, world, event, type/schema, payload, creation time, and attempt count; only lock/publication state and canonical availability time are reset. Exact retry-UUID replay returns the original intent plus current message status/attempts. If the message later becomes dead again, a new reviewed retry identity is required.

## Scheduled effects

Milestone 09 extends the M07 process registry from 1 to 2 without changing schedule, action, process, queue, failure, projection, outcome, or PRNG schemas. Schedule payloads contain only a target UUID:

| Action type               | Target            | Narrow system command                                                    |
| ------------------------- | ----------------- | ------------------------------------------------------------------------ |
| `CompleteProductionRunV1` | `productionRunId` | Complete the exact pending run and its reservations.                     |
| `SettlePayrollV1`         | `payrollRecordId` | Settle the exact pending wage/tax snapshot.                              |
| `ExpireMarketListingV1`   | `listingId`       | Release the exact open listing remainder after its expiry tick.          |
| `AssessPeriodicTaxV1`     | `taxPolicyId`     | Assess one exact due policy occurrence and schedule the next occurrence. |

The worker actor is `worldgraph:commerce-scheduler`. Its idempotency key is `commerce-schedule-v1:<ActionType>:<scheduledActionId>`, and causation is the completed scheduled-action event. Duplicate wake, restart, or retry therefore resolves to the original command result.
