Clock initialization resolves the active compiled `simulation_configuration -> uses_primitive -> simulation.discrete_clock` relationship first. Compiled settings override defaults; the clock primitive supplies `tickDurationSeconds` and `maxCatchUpTicks` when settings omit them. Provenance is `compiled_configuration` only when every selected compiled value is valid; an invalid selection falls back atomically to the complete default set and records `m07_default`, rather than silently mixing values or overstating provenance. The sealed fallback is epoch `2000-01-01T00:00:00.000Z`, 86,400,000 world milliseconds per tick, 10,000 ms wall cadence, 64 ticks per batch, and 256 catch-up ticks. Bounds are enforced in PostgreSQL: tick duration 1..31,536,000,000 ms, cadence 100..86,400,000 ms, batch 1..256, catch-up 1..4096 with catch-up at least batch, and schedule priority -1000..1000.

Architecture decision: `worldgraph_simulation_projection_checksum` is intentionally separate from the M06 graph checksum and hashes semantic simulation state only. It includes clock configuration/current tick/mode/PRNG/cumulative outcome hash plus schedule head and each action's deterministic sequence, due tick, priority, type/schema, payload hash, process version, and status. It excludes row/state revisions, command/event/schedule UUIDs, timestamps/wall anchors, worker identities, fencing data, and batch/failure execution metadata. Consequently equivalent outcomes retain the same final checksum across worker identities and one-batch versus split-batch execution, while storage and API records keep the excluded operational evidence.

### Restricted tally-role prerequisite for `0013`

`0013` deliberately does not create a cluster login role or embed a credential. Before applying a pending `0013`, a PostgreSQL cluster administrator—not the application or migration process—must provision `worldgraph_governance_tally` as `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT`, give it `CONNECT` only to the target database, and issue a unique credential through the deployment secret manager. The role must not own database objects or belong to a privileged role. Inspect the flags and memberships before migration:

```sql
SELECT rolcanlogin, rolsuper, rolcreatedb, rolcreaterole, rolinherit
FROM pg_catalog.pg_roles
WHERE rolname = 'worldgraph_governance_tally';

SELECT pg_catalog.pg_get_userbyid(roleid) AS granted_role
FROM pg_catalog.pg_auth_members
WHERE member = (
  SELECT oid FROM pg_catalog.pg_roles WHERE rolname = 'worldgraph_governance_tally'
);
```

If the role is absent, the cluster administrator may create the credential-free role boundary with:

```sql
CREATE ROLE worldgraph_governance_tally
  LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT;
```

Set or rotate its password with approved secret-manager/DBA tooling that does not expose the value in source, shell history, logs, or tickets; then grant `CONNECT` on the named deployment database. Supply the separately managed URI only as `GOVERNANCE_TALLY_DATABASE_URL` to the governance worker. Never reuse `DATABASE_URL`, `MIGRATION_DATABASE_URL`, or `OPERATIONS_DATABASE_URL`. Migration `0013` fails before installing governance objects when the role is absent or over-privileged; fix the external role and safely rerun the unchanged migration. After migration, validate with the restricted credential that approved aggregate tally reads/functions work and direct users, membership/eligibility linkage, ordinary application tables, and all mutation attempts remain denied.

Rotation is stop-and-verify: pause governance scheduling, rotate the database credential and deployment secret, restart only the tally-using worker, require readiness, rerun the restricted positive/negative privilege checks, and then resume. If the migration or deployment must be abandoned, keep governance workers stopped and set the unused tally role to `NOLOGIN` or rotate it; do not drop a role that an applied migration grants to, and do not remove individual M10 objects. Restore/PITR the whole database or apply a reviewed forward correction.

Run `pnpm db:migrate` with owner-only `MIGRATION_DATABASE_URL` to migrate, or `pnpm --filter @worldgraph/db bootstrap` to migrate and import the reviewed primitive catalog. Both are safe to repeat at head. Compose uses the bootstrap as a one-shot prerequisite; API and worker startup never migrate.

Never edit a shared migration. Add a reviewed forward migration. There is no destructive down migration: stop incompatible code, restore/PITR if required, or append a forward repair.
